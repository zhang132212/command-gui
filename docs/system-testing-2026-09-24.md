## 执行结构

`testing/run-system-tests.ps1` 按顺序运行六个阶段：服务端套件及重启、集成服务端（有 Carpet）、集成服务端（无 Carpet）、专用服务端加两个 TCP 客户端、界面布局、测试运行器自检。失败后继续其他独立阶段，缺失证据不视为通过。

专服联测先编译实际产品 JAR 和仅用于测试的 QA JAR，再启动三个 JVM。客户端 A 为 OP，客户端 B 从普通玩家变为白名单编辑者，再被撤销权限。二者分别断线重连，观察同步与缓存清理。GUI 点击通过实际控件事件派发；复杂时间线和检测器测试数据通过编辑器模型填充，再经实际保存与网络链路提交。

QA 协议只创建隔离世界的检测方块、协调角色进度和读取服务端状态；机器操作、规则修改和数据查询使用产品本身的 Fabric 载荷与处理器。测试混入代码只观察包、系统消息和执行命令，不替换产品处理器。

## 本次修复的产品边界

- 在变更前验证 JSON 字段的真实类型和整数范围，防止 Gson 隐式转换让字符串布尔值释放编辑锁，或让错误类型的模式集合触发停止。
- 编辑必须带匹配的非负修订号，缺失或伪造修订号不能绕过并发控制。
- 模式请求含未知 ID 或多个单选模式时整批拒绝，保留现有运行状态。
- 禁止机器 ID 使用调度器模式键分隔符 `#`，避免跨机器运行状态相互干扰。
- 配置文件必须明确包含机器数组；损坏或缺字段时保留已加载配置，显式空数组仍可清空。
- 修订号使用 64 位整数，覆盖超过 32 位上限的合法保存；耗尽 64 位范围时明确拒绝而非溢出。

## 证据解释

HTML 汇总、JSON、JUnit、原始 stdout/stderr、Minecraft 日志、JSONL 事件和截图位于同一个结果目录。事件包含 UTC、进程内单调时间、线程、序号、完整模组载荷、GUI 操作、断言和服务端执行记录。源文件与证据 SHA-256 用于定位本次实际测试版本。

故意注入的失败请求和超时会产生错误日志，判断 bug 应结合对应断言与事件顺序。抓包和逐条写日志会增加运行开销，因此这些时间数据用于定位停顿，不作为无插桩性能基准。

自动化覆盖列出的功能和边界，不等于穷尽全部输入、第三方模组组合、操作系统、断电、磁盘写满或任意丢包。测试源码和失败证据一并保留，方便新增种子与复现问题。
